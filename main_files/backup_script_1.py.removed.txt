   Its RESOURCES each say what they already ARE in this codebase, and each carries a
   NOTE: one line from the requirements stage on what the resource is, where its value
   comes from (which input, which schedule it is read off), why it is bound as it is, and,
   for a word the query leaves undefined, that it is undefined. Use the note to tell apart
   resources with the same "is" line and, for a
   resource on a hasInput edge of the algorithm, to obtain it the way the note says it
   arrives. A note is context, not a decision: it never overrides the "is" line.
   A resource's NAME is the requirements stage's name for it: where an environment step
   or a representation choice serves a resource, name that resource in its reason.
   - A resource whose "is" line names ONE thing is settled AS A TYPE — do not re-decide
     it. A binding says what a value IS, never where it comes from: two resources with
     the same "is" are two VALUES
     of one type, each obtained separately.
   - A resource whose "is" line names SEVERAL schedule forms (by PART 2 id, or by the
     code PART 2 lists for each) is the requirements stage
     telling you exactly which choice it left open and left to you: that is the choice
     step 3 asks you to make, already narrowed to the forms that would be correct. A
     resource bound to ONE STREAM'S PART of those forms (candidate_array[:, i] or
     Schedule.slots_by_stream(i)) follows the same choice: it is the part of the form
     `schedule` names, and reading it off a schedule is algorithm work.
   - A resource whose "is" line says it has to be BUILT is algorithm work, and no
     environment step settles it.
   - A resource whose "is" line is a KEY of a library dict, written as the code that
     reaches it (such as Usecase.streams[i]['pathLists']), names a field of one use
     case's data. No environment step obtains it, and which schedule its value is read
     off is algorithm work.

   Its TRIPLES are subject-predicate-object edges under each requirement. The ones that
   concern you are hasInput and hasOutput whose SUBJECT is the algorithm being built:
   they say what the algorithm is handed and what it must produce, so each resource on
   such a hasInput edge must be obtained by an environment step (step 4). A hasInput
   edge whose subject is one of the algorithm's own steps is
   data the algorithm passes to itself, not environment. The rest are not yours:
   hasStep, precedes, criterion, minimizes, mustSatisfy and precondition all describe
   what the algorithm DOES, and an environment step claiming to settle one of those is
   the mistake this stage exists to avoid.


=== blueprint section 3 ===
3. REQUIREMENT MAP — for every requirement id in the ledger EXCEPT the ones listed below
   as already satisfied by the configuration, the name(s) of the function(s) in the
   inventory that satisfy it. Every other id must appear, with at least one real function
   name against it: a requirement with no function is incomplete and must be fixed by
   adding a function or attaching it to an existing one.
   The already-satisfied ids are OMITTED from this map entirely. Do not list them with an
   empty function list — an id is either mapped to real functions or absent, and absent
   means the configuration owns it. Those ids are already recorded, with a line each on
   how, in the configuration's own requirement coverage; repeating them here with nothing
   against them loses that and states nothing.


=== blueprint section 5 ===
5. RESOURCE USE — one entry per resource in the ledger, in the ledger's order:
     - "resource": its name, copied exactly;
     - "used_as": the names of the data structures or functions above that
       carry it, a field written Structure.field, an enum value written Type.VALUE (Type
       being the enum's owner, also for an enum named Type.field) - several where the resource is split
       across elements, the same element under several resources where they are merged;
     - "reason": empty when used_as names something; otherwise one line on why this
       design needs nothing for it.
   Every resource appears exactly once. This is what makes the requirements stage's names
   fully used: each one is either built upon or set aside with a reason, never dropped
   silently.

They are finished, not deferred. You will not find them in the ledger, you must not add

These were removed only because the environment genuinely completes them — supplying an

Requirements ledger:
{requirements_ledger}

HOW TO READ THAT GRAPH INTO THIS DESIGN. The ledger above comes with a graph: the
RESOURCES the requirements are about, with what each one already IS in the codebase, and
the TRIPLES saying how they relate. Each kind of line maps onto something you must
produce, and a line you ignore is a requirement you have dropped.

  the RESOURCES      Each is a thing the algorithm handles, and its "is" line already
                     says what it IS in the codebase. Where you realise a resource as a
                     data structure, its corresponds_to is that "is" line — copy it, do
                     not re-decide it — and a resource whose "is" says it must be BUILT
                     has corresponds_to null. Its NAME is the requirements stage's name for
                     it: use each name as fits your design - as the name of a structure,
                     a function (its snake_case form) or an enum value; on
                     its own, merged with others into one element, or not at all - and
                     record that choice for EVERY resource in RESOURCE USE (section 5).

  a resource's note  One line from the requirements stage: what the resource is, where
                     its value comes from (which input, which schedule it is read off),
                     why it is bound as it is, and, for a word the query leaves
                     undefined, that it is undefined. Its structure's "why", and the
                     function listing it under "writes", must agree with where the note
                     says the value comes from, and a resource the note calls undefined needs a definition -
                     the Literal type that spells out its cases, or the "<Name> = ..."
                     expression in the purpose of the function that computes it. It never
                     overrides the "is" line.

  hasInput/hasOutput What is handed to something and what it produces. These are your
                     signatures, and they are also the reads and writes you declare: a
                     resource on a hasInput edge is READ by the function doing that
                     work, one on a hasOutput edge is WRITTEN by it.

  hasStep            Each object is an action the design must perform, so each needs a
                     function — not a comment inside a larger one. The SUBJECT says
                     whose steps they are: the steps of one strategy belong to that
                     strategy's function, not to the orchestrator.

  precedes           The order those functions run in. Where it is present it is not
                     advice: a design that could emit them in another order has not
                     satisfied it.

  precondition       Something that must HOLD before its subject may run, so the subject
                     needs a function that CHECKS it and refuses otherwise. A step that
                     proceeds without checking its precondition is the commonest way
                     these designs fail.

  mustSatisfy        A quality something must have. If its object is a resource that has
  minimizes          to be built, nothing in the library computes it and YOUR design
                     must: name the function that produces it, and make sure that
                     function lists the object under "writes". A quality with no
                     producer is an obligation this design only claims to meet.

  criterion          What a choice is ranked by. The subject is the thing being chosen,
                     so it needs a function that scores candidates and orders them by
                     the object. Two criterion edges with different subjects are two
                     different choices needing two different rankings.

  isA                The subject is ONE CASE of the object. So the object is the general
                     thing your design selects among, and a design handling only the
                     named case has ignored the word "one": there must be a function
                     that chooses, and something else for it to choose between.

  appliesWhen        The subject is used only in the situation the object names. The
                     function that chooses the subject must test that situation and
                     offer the subject only when it holds.

  transformsFrom     The subject starts from / arrives at the object: the function that
  transformsInto     produces the subject makes the object its first / its last element.
  mustEndAt          The same obligation as transformsInto, stated as a requirement on the
                     result: the last element must equal the object.

  partOf             The subject is a piece of the object: the object's type holds values
                     of the subject's type, directly or through a record it holds.

  determines         The subject decides the object: the object is written by the
                     function that realises the subject, or by one that function calls.

  builtBy            The subject is constructed by means of the object: the object is the
                     top-level function, and it is the one that realises the subject.
